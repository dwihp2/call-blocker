# Matching runs in native code on both platforms, with a fixture table as the contract

Android's call screening service can't call JavaScript when a call arrives, and iOS has no per-call code at all: its extension compiles the Rules into a flat list the system consults. Both sides therefore need the pattern matching and precedence rules in their own language — Kotlin for Android's live match, Swift for iOS's compile. TypeScript keeps parsing and validation (`libphonenumber-js` writes Canonical numbers, so both platforms and Backup files agree on what a number is), storage, and the UI; the native engines only ever see canonical input.

Two implementations of one semantics drift unless something makes drift visible, so the contract is a checked-in fixture table: cases of Rules, Contacts allowance and a number, with the expected decision. Kotlin unit tests run it on the JVM on every push; the Swift side runs the same file from XCTest on Mac builds. Rejected alternatives: a shared Rust/C++ core compiled into both through UniFFI and JNI (one source of truth, but a toolchain nobody on this project has reason to learn), and keeping a TypeScript matcher as an oracle (a third implementation, and the one closest to the code nobody ships).
